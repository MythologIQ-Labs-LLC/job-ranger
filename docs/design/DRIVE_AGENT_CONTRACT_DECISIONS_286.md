## Product invariant

**Agent-first means substantial, autonomous, durable, versioned WORK in an agent-owned namespace, not agent authority over Job Ranger's confirmed facts.** The UI may be closed for months. An authorized agent can research, annotate opportunities, write and revise materials, and plan activities through original structured JSON plus selected attachments. Job Ranger must be able to deterministically reconcile that work on return, including forks, stale evidence, replays and incomplete uploads. No Drive file grants approval, confirms a credential, changes a canonical application status, executes an inference result as a Truth Gate PASS, modifies local SQLite/OPFS directly or supplies its own permissions.

Read-only immutable export + local receipt remains distinct from:
1. agent-owned append-only work versions;
2. consequential proposals staged for existing user/governance checks;
3. full private `.jobranger` recovery archives with **no default agent access**.

## Fourteen decisions from implementation review

| # | Decision | Implementation impact / acceptance |
|---|---|---|
| **D01: Completion marker** | **Adopt `jr-agent-batch-commit` v1**, matching the *implemented* provisional parser, rather than the audit-only `jr-agent-batch-complete` name. The final sidecar `<batch_id>.commit.json` must contain `format`, `schema_version`, `batch_id`, `batch_sha256`, exact `batch_bytes`, and a closed bounded inventory `attachments[{path,media_type,bytes,sha256}]`. Publish **last**, then read back original MIME metadata and bytes. The final marker is a completeness marker **not** cryptographic agent identity, user consent or a Drive transaction. |
| **D02: Attachment references** | **Adopt explicit per-draft references** in `material_draft_version.payload.attachments[]`, keyed by exact content digest and safe relative path, and require an exact membership match with the batch completion marker. No unrelated marker-only attachments can influence accepted work. Up to the reviewed size/count caps, original PDF/DOCX/Markdown/plain-text MIME only. Provider conversion to native Google Docs is not valid machine input. This requires a runtime/schema/test change; it does not exist in G2. |
| **D03: Application statuses** | **Keep a user-facing claimed-status vocabulary distinct from canonical `ApplicationStatus`**, with a **closed versioned mapping** into canonical values solely for comparison/display: `drafted→interested`, `submitted→applied`, `interviewing→interview`, `offered→offer`, and explicit mappings/unsupported handling for `rejected`/`withdrawn`. A matching claim **never** proves the application was actually submitted or transitions canonical status. Review UI must label the distinction. |
| **D04: Agent record base** | For agent-owned drafts and application-status *claims*, `base_revision=null` at the operation level; prior agent versions are linked by `previous_operation_id` and their stable `record_id`. For corrections to canonical evidence, `base_revision` must equal the precise currently referenced canonical evidence revision. A new qualification proposal has `base_revision=null`. Enforce operation-kind-specific combinations in semantic validation. |
| **D05: New qualification** | **Distinguish new versus correction explicitly** with `proposal_kind:\"new\"|\"correction\"`. New: `evidence_id=null`, no preexisting target; correction: concrete `evidence_id` and mandatory base revision. Both remain unconfirmed proposals; evidence references establish *claims of support* only and must pass domain/source/user gates. Do not use a fabricated evidence ID to imply a canonical record exists. |
| **D06: Export scopes** | Add separately selectable, identity-minimized **`career_direction`** (target titles/sectors/interests where approved, not contact identity) and **`selected_applications`** (explicit user-selected stable IDs and minimal lifecycle context, never private notes/contact history by default). Do not silently export all applications or expand `drive.file` OAuth scope. This is an explicit selection/consent change requiring round-trip tests. |
| **D07: Evidence revision** | Treat `updatedAt` as the **G2 compatibility revision**, not a strong causal identity. Design a monotonic local revision (or collision-resistant version token over canonical evidence fields + stable ID + namespace) under a migration, with deterministic change detection. Never derive ordering/authority from timestamps. Round-trip migration must still recognize older exported revisions and flag ambiguous stale citations. |
| **D08: Source revision** | Retain a stable `sha256:` digest of the canonical *selected source snapshot* as the G2 export basis; freeze its field selection, stable sorting and canonical JSON serialization. This is a **change detector, not a signature** or cross-device trust bootstrap. Tie receipts to the local installation/workspace identity, explicit selection and export manifest digest. |
| **D09: Fork/conflict policy** | **Both** competing same-parent revisions are staged; none wins from Drive listing order, authored timestamp or actor name. Within one import set, **every** content variant of the same operation ID is quarantined if hashes disagree. Across import sessions, [#289](https://github.com/MythologIQ-Labs-LLC/job-ranger/issues/289) requires durable contest status on any earlier imported draft, preserving both byte versions and blocking auto-promotion. This is an explicit **G3 blocker**; current G2 PASS does not demonstrate persisted downgrade. |
| **D10: Proposal duplication** | **One ingestion path in v1:** consequential changes use closed `jr-agent-operation-batch` operations (including `evidence_change_proposal` and `application_status_claim`). Retire the separate `jr-agent-proposal` v1 *from active import* for this milestone; retain its prior draft file only as deprecated design history and document the migration. Do not implement two semantically different approval paths to the same canonical action. |
| **D11: Closed local formats** | Publish candidate JSON Schemas for `jr-agent-export-records`, `jr-agent-export-receipt`, `jr-agent-reconcile-ledger` and completion markers. Receipts, ledger, idempotency and trust/permission state stay in trusted local app storage **outside the agent-writeable Drive folder**, with atomic writes, recoverability, quota and corruption tests for PWA and Electron. Unknown key/version fails closed. A remote manifest cannot reconstruct a lost local trusted receipt on a new device. |
| **D12: Operation IDs / actor separation** | Retain globally unique opaque `operation_id` plus stable agent namespace/ID for collision reduction, but **do not assume an agent-claimed ID authenticates a writer**. A configured writer namespace should be anchored to the locally approved Drive folder/file ID or separately authenticated principal where feasible. Any spoofed actor namespace or same-ID/different-content operation is a conflict, never an accepted update. No automatic namespace trust based on a file path. |
| **D13: Discovery and batch linkage** | The human-readable path `workspace/agents/<actor_id>/batches/<batch_id>.json` is a **convention and validator constraint**; for real Drive access, bound containment uses opaque Drive file/parent IDs and original MIME. On intake compare `workspace_id` with a trusted local receipt/configuration; reject mismatch, not merely warn. Require prior `previous_batch_id` in the same claimed append-only actor chain or deliberately stage as `incomplete/pending` with explicit recovery semantics, never silently import causally dependent records. |
| **D14: Exclusions manifest** | `excluded_by_default` is a **stable privacy-policy class list**, not a live report of which fields were actually omitted. Keep deterministic full list for reproducibility. Add separate machine-readable selected/omitted scopes and export receipts if per-export disclosure detail is needed. Never infer authorization from an exclusion string; consent always comes from trusted local policy. |

These decisions deliberately separate **already implemented G2 semantics** from **G3/G4 format or authorization changes**. In particular, D02, D05, D06, D07, D09 (persisted ledger), D11, D12, and D13 need implementation/negative tests before promotion to normative supported v1. Design approval alone does not validate code.

## Cross-system acceptance gates

**A. Contract / fail-closed tests:** Closed JSON-Schema and executable validator must agree on object field sets, kind vocabularies, status mapping, exact attachment lists, marker bytes/digests, path rules, missing source refs, and disallowed privilege keys. Use the independent 31-case audit corpus and original-binary fixture compiler; do not silently swap an accepted schema version while an agent is writing.

**B. Durable local state:** The PWA and Electron persistence seam must store receipts, operation ledger, drafts, staged consequential proposals, quarantined bytes, pending causal parents and durable contested markers transactionally. On browser restart, resuming from Drive must not duplicate drafts or change canonical facts. Simulated 60-day two-agent return must pass.

**C. Review/import experience:** Ordinary agent-owned drafts can be saved under explicit local standing user permission. Evidence changes, status claims and approved materials always require relevant domain gate + human review. No inference-generated `approved` flag is accepted. Reviewer sees exact source evidence/revision, stale flags, fork alternatives and outcome audit trail.

**D. Google transport:** Only user-approved normal visible Drive folders, real Google-issued authorization, minimal permissions, original binary/text blobs, last-published commit marker, re-download digest checks, pagination, provider IDs/parent checks, reauthorization/offline recovery. Browser short-lived token restrictions and native PKCE credential custody are distinct, #264 isolation remains binding.

**E. New-device bootstrap:** No remote self-attested receipt may become the trusted local root. Specify secure recovery via existing vetted backup with the receipt/ledger (or an explicitly reviewed alternative) before claiming cross-device canonical synchronization.

**F. Parallel delivery:** Continue #194 release hardening including #282/#288 data integrity work; provider candidates #283/#284 remain deferred. No PR merging, hosted Actions spree, tag, or production OAuth adoption without separate owner authority and exact-head review.

## Known compatibility divergences in the independent audit lane

Independent [audit branch](https://github.com/MythologIQ-Labs-LLC/job-ranger/tree/audit/286-agent-schema-adversarial-corpus) previously named the marker `jr-agent-batch-complete` and used a separate top-level attachment field, whereas G2 implementation uses `jr-agent-batch-commit` and places attachments in the marker. **Do not cherry-pick mismatched audit schemas into runtime.** Normalize these explicitly under D01/D02 and modify fixtures/tools in the same change. The standalone oracle remains useful as *semantic* acceptance evidence, not as evidence of an already compatible serialized transport.

**No release claim:** G2 is local and independently reviewed. This record sets the contract reconciliation criteria before G3 UI/storage and G4 OAuth. Nothing here grants agent canonical write authority, says Drive is connected, or reopens provider-specific integrations.
